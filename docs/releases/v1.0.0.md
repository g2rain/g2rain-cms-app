# v1.0.0 · G2rain CMS 内容管理微前端

`g2rain-cms-app` 是 G2rain（谷雨）开源智能体平台中的 CMS 业务微前端：它提供站点、空间、栏目、页面、文章、分类和标签的管理界面，并作为 qiankun 子应用由 `g2rain-main-shell` 装载，调用 `g2rain-cms` API。它不拥有 CMS 领域数据或服务端规则，也不代表、替代或单独交付整个平台能力。平台当前已具备应用开发、部署和使用基础；SaaS 基座现有能力与知识库可用，智能体平台和智能客服已开发完成并开源，交易、订阅和计量计费等商业化能力仍处于规划设计。具体能力和接入状态以 [G2rain 中央仓库](https://github.com/g2rain/g2rain) 为准。

## 构建与运行

项目版本事实源为根目录 `package.json` 和 `package-lock.json`，本版均为 `1.0.0`。要求 Node.js 22+ 和 npm；`npm ci --legacy-peer-deps` 安装锁定依赖，`npm run build` 执行 `vue-tsc` 类型检查及 Vite 生产构建。项目没有 `test` 或 `lint` 脚本，因此完整构建是当前 CI 的全部自动验证范围，不等同于浏览器联调、容器运行、匿名拉取或实际部署验证。

容器复用根目录 `Dockerfile` 与 `build.sh`：Node 22 Alpine 构建静态产物，OpenResty Alpine 运行，入口为 `/docker-entrypoint.sh`，Dockerfile 声明端口 `8080`；运行时默认 `SERVER_PORT=80`，部署须显式映射端口。镜像启动时渲染 Nginx 模板，并注入 `SSO_BASE_URL` 到 `env-config.js`。生产环境应关闭 Mock，并通过环境变量提供 Gateway/IAM 地址、Context Path 和 SSO 地址。

## GHCR 发布

- 镜像：`ghcr.io/g2rain/g2rain-cms-app`。
- 仅严格格式的稳定 Git tag（如 `v1.0.0`）会触发工作流；普通分支、Pull Request 和手动触发均不会发布。
- 工作流要求 tag 提交已进入 `main` 历史，且该提交包含本说明；它校验 tag、`package.json` 和 `package-lock.json` 版本一致，再运行 `npm ci --legacy-peer-deps` 与 `npm run build`。
- 成功时仅推送 `1.0.0` 与 `sha-<完整提交 SHA>` 标签，不创建 GitHub Release、不部署服务，也不更新 `latest`。
- OCI 元数据包含 source、url、title、version、revision 和与仓库 LICENSE 一致的 `Apache-2.0` 许可证。

先按 `feature/* → develop → main` 流程将发布改动和本说明合入 `main`，验证该提交后再创建并推送 tag。完整权限和操作见[部署文档](../operations/deployment.md#github-container-registry-ghcr)。

## 镜像内容与安全

最终镜像包含 Vite `dist`、Nginx 模板、启动脚本、Lua 签名实现和离线 `luaossl` 构建结果；不包含 Node 依赖或源码。`.env.production` 是已跟踪的构建配置，会进入构建上下文；当前只含占位符与路径配置，维护者仍须在每次发布前审查其中是否出现私有地址或凭据。`lua/keys/` 已由 Docker 忽略规则排除，且最终镜像仅创建该目录；私钥、IAM 公钥和 key ID 必须通过受控 volume、Secret 或等效部署机制在运行时注入，绝不可构建进镜像。

Docker 忽略规则不改变已跟踪文件的公开性。公开镜像前，维护者必须确认 Git 中不存在 Token、私钥、默认凭据或不应公开的地址。生产验收仍需覆盖 Context Path 刷新、Gateway/IAM/SSO 联调、密钥挂载、代理和静态缓存；本次发布准备未执行 GHCR 推送、匿名拉取或实际部署。

2026-11-02 的发布准备检查已确认版本 JSON 一致、`git diff --check` 通过，并人工核对工作流的触发、tag/分支/发布说明/版本校验以及两标签推送路径。本机现有 `node_modules` 缺少 `@g2rain/*` 包，直接执行 `npm run build` 因无法解析这些模块而失败；随后 `npm ci --legacy-peer-deps` 又因 Windows 锁定 `node_modules/.package-lock.json`（EPERM）无法清理安装目录。Docker Desktop Linux engine 未启动且 Buildx 锁无访问权限，故未执行镜像构建或镜像内容运行时检查。CI 采用干净安装并为仅构建所需的本地 CLI 依赖创建 stub，仍须以首次 Actions 运行结果确认。
